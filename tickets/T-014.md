# T-014: Connect a home to Home Assistant
- Milestone: M1
- Depends on: T-013, T-003
- Use cases: UC-12
## Goal
A member saves the HA URL and token with `PATCH /api/homes/{id}`; the backend checks them against HA, encrypts the token and returns rooms and device counts.
## Definition of Done (copied from use cases)
- [ ] AC-12.1 Given the right URL (`http://homeassistant:8123`) and token, when the member saves them, then the response is `200` with `ha_connected: true`, `ha_url`, `rooms: 3` and `devices: 11`.
- [ ] AC-12.2 Given the home is connected, when any home route returns the home, then the response has no `ha_token` field and does not contain the token anywhere.
- [ ] AC-12.3 Given the home is connected, when the developer reads `homes.ha_token_encrypted` in SQLite, then the value is not the token (it is Fernet-encrypted).
- [ ] AC-12.4 Given the home is connected, when the developer searches the backend logs for the token, then it is not found.
- [ ] UC-12-E1: Given a wrong or deleted token, when the member saves it, then the response is `400` "Home Assistant rejected the token" and nothing is saved.
- [ ] UC-12-E2: Given a URL where nothing answers (`http://homeassistant:9999`), when the member saves it, then within 10 seconds the response is `400` "Can't reach Home Assistant at http://homeassistant:9999" and nothing is saved.
- [ ] UC-12-E3: Given a value that is not an `http` or `https` URL (`homeassistant`), when saving, then the response is `422` "Invalid URL".
- [ ] UC-12-E4: Given a URL with a trailing slash (`http://homeassistant:8123/`), when saving, then it is accepted and stored without the slash.
- [ ] UC-12-E5: Given only `ha_url` is sent without `ha_token` on a home that has no token yet, when saving, then the response is `422` "ha_url and ha_token are needed together".
- [ ] UC-12-E6: Given the home is already connected, when the member saves a new valid token, then the new one replaces the old one and the connection keeps working.
- [ ] All tests pass. Reviewer approved. Verifier passed.
## Technical notes
- `backend/app/core/crypto.py`: `encrypt_token`, `decrypt_token` with Fernet (`HA_TOKEN_KEY`). Decrypt errors raise a typed error (used in T-015 for UC-12-E7).
- `backend/app/ha/client.py` (first part): a one-shot `fetch_home(url, token)` that opens HA's WebSocket (`/api/websocket`), authenticates, calls `config/area_registry/list`, `config/device_registry/list`, `config/entity_registry/list`, `get_states`, and closes. Typed errors: `HATokenRejected`, `HAUnreachable` (10 s timeout).
- `backend/app/ha/model.py`: build the home model from registry data: supported entities (`light`, `climate`, `fan`, `sensor` with device_class temperature/humidity), each with its area (own or via device). Count rooms that have supported entities and devices (a sensor device with two entities counts once). This builder is reused by T-016.
- `PATCH /api/homes/{id}`: `ha_url` (http/https only, trailing slash removed) and `ha_token` must come together if the home has no token yet; on success save both and return `ha_connected: true`, `ha_url`, `rooms`, `devices`. On failure save nothing.
- Error text exactly as the use cases. Never log the token; never include it in any response model.
- Accepted risk (record it in the report, T-058): the backend connects to whatever `ha_url` a member enters (server-side request forgery into the Docker network). Blocking private addresses would also block `http://homeassistant:8123`, so for this localhost POC the limits are: http/https only, 10 s timeout, members only.
- Pin `httpx`, `websockets`, `cryptography`. Mock HA in tests (fake WebSocket server or patched client).
- Tests: `tests/test_homes_connect.py` (every AC and edge case, token never in responses, encrypted value differs from token) and `tests/test_ha_model.py` (counting, unsupported entities skipped).
## Manual test steps
Needs T-002 (token) and T-003 (devices in HA).
1. ```bash
   curl -i -b a.txt -X PATCH $BASE/homes/$HOME_A -H 'Content-Type: application/json' \
     -d '{"ha_url":"http://homeassistant:8123","ha_token":"<token from T-002>"}'
   ```
   Expect `200`, `ha_connected: true`, `rooms: 3`, `devices: 11`, no token in the body.
2. `curl -b a.txt $BASE/homes/$HOME_A | grep -c "<first 20 characters of token>"`. Expect `0`.
3. `sqlite3 data/app.db "select ha_token_encrypted from homes;"`. Starts with `gAAAA`, not your token.
4. `docker compose logs backend | grep -F "<first 20 characters of token>"`. Expect nothing.
5. E1: send `"ha_token":"wrong"`. `400` "Home Assistant rejected the token"; `ha_connected` unchanged.
6. E2: send `http://homeassistant:9999`. Within 10 s `400` "Can't reach Home Assistant at http://homeassistant:9999".
7. E3: send `"ha_url":"homeassistant"`. `422` "Invalid URL".
8. E4: send the URL with a trailing slash; the saved `ha_url` has no slash.
9. E5: on the second home (no token), send only `ha_url`. `422` "ha_url and ha_token are needed together".
10. E6: create a new token in HA, save it; still `ha_connected: true`.
11. `cd backend && pytest`.
