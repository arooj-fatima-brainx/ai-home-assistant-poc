# T-051: Latency per stage for voice turns
- Milestone: M3
- Depends on: T-050
- Use cases: UC-44
## Goal
Every voice turn records `stt_ms`, `llm_ms`, `device_ms`, `tts_ms` and `total_ms` in `request_metrics`.
## Definition of Done (copied from use cases)
- [ ] AC-44.1 Given a voice turn, when the developer reads `request_metrics`, then `input_mode` is `voice` and all five timings are filled in.
- [ ] AC-44.2 Given a voice turn, when the timings are added up, then `stt_ms + llm_ms + device_ms + tts_ms` is not more than `total_ms`.
- [ ] UC-44-E1: Given mute is on, when a voice turn runs, then `tts_ms` is still recorded (speech is made on the server; mute only stops playback).
- [ ] All tests pass. Reviewer approved. Verifier passed.
## Technical notes
- Reuse the stage timer from T-031 in `voice/router.py` for `stt` and `tts`; `input_mode="voice"`; `total_ms` measured around the whole request.
- TTS always runs on the server for voice turns, even when the browser is muted (mute is playback only).
- Tests: a voice request with STT, LLM and TTS mocked writes all five timings and the sum is not more than `total_ms`.
## Manual test steps
1. Speak 3 commands in the app (one with mute on).
2. `sqlite3 data/app.db "select input_mode, stt_ms, llm_ms, device_ms, tts_ms, total_ms from request_metrics order by id desc limit 3;"` -> `voice`, all five filled, the sum of the four stages not more than `total_ms`; the muted turn still has `tts_ms`.
3. `cd backend && pytest`.
