# T-026: Several actions at once and partial failures
- Milestone: M2
- Depends on: T-025
- Use cases: UC-21, UC-28
## Goal
Several tool calls in one turn run at the same time; each device gets its own result, and one failing device never blocks or hides the others.
## Definition of Done (copied from use cases)
- [ ] AC-21.1 (T8) Given the kitchen light is on and the bedroom fan is off, when the member says "Turn off the kitchen light and set the bedroom fan to 3", then the kitchen light is off and the bedroom fan is on at speed 3.
- [ ] AC-21.2 Given T8, when the `results` list is checked, then it has one entry per device, both `ok`.
- [ ] UC-21-E2: Given one valid and one out-of-range request ("turn on the kitchen light and set the bedroom AC to 35"), when it is sent, then the kitchen light turns on and the reply says the bedroom AC allows 18 to 28 °C (the valid part is not blocked).
- [ ] AC-28.1 (T15) Given the bedroom fan is offline, when the member says "Turn on the bedroom fan", then the reply says the fan isn't responding, and the result is `failed` "device offline" in under 0.5 s of device time.
- [ ] AC-28.2 (T16) Given the bedroom fan is offline and the kitchen light is off, when the member says "Turn on the kitchen light and the bedroom fan", then the kitchen light is on and the reply says the bedroom fan failed.
- [ ] AC-28.3 Given the kitchen light has `ignore_commands`, when the member says "Turn on the kitchen light", then after about 3 seconds the result is `timeout` and the reply says the light did not confirm (never "done").
- [ ] UC-28-E1: Given the fan comes back online (`normal`), when the member asks again, then it works.
- [ ] UC-28-E2: Given the bedroom fan is offline, when the member asks "What's on?", then the fan is reported as not responding.
- [ ] All tests pass. Reviewer approved. Verifier passed.
## Technical notes
- `agent/loop.py`: run every tool call of one response with `asyncio.gather(..., return_exceptions=True)`; an exception in one tool becomes a `failed` result for that device only.
- `agent/prompts.py`: report each device's outcome; for `failed` say it isn't responding; for `timeout` say it didn't confirm; never "done" for non-`ok`.
- Offline -> `failed` "device offline" without an HA call (M1 guard); `ignore_commands` -> `timeout` after `DEVICE_CONFIRM_TIMEOUT`.
- AC-21.3 (timings) is in T-031.
- Tests: fake LLM returns two tool calls, one tool sleeps; total time is close to the slower one; one raises -> other still `ok`.
## Manual test steps
Setup for every M2 manual test (from `docs/use-cases.md` M2 conventions): log in as Ali (`a.txt`), `export HOME_A=<id>`, start a conversation and `export CONV=<id>`, then define:
```bash
say() { curl -s -b a.txt -X POST $BASE/homes/$HOME_A/conversations/$CONV/messages \
  -H 'Content-Type: application/json' -d "{\"text\": \"$1\"}" | python3 -m json.tool; }
new() { export CONV=$(curl -s -b a.txt -X POST $BASE/homes/$HOME_A/conversations | python3 -c 'import sys,json; print(json.load(sys.stdin)["id"])'); echo $CONV; }
```
Reset devices with the on/off endpoint (T-018) or the HA UI before each scenario. Check the meaning of the reply and the state in HA, not the exact words.
1. Kitchen light on, bedroom fan off. `say "Turn off the kitchen light and set the bedroom fan to 3"` -> both changed in HA; `results` has 2 `ok` entries (T8).
2. E2 (UC-21): `say "turn on the kitchen light and set the bedroom AC to 35"` -> kitchen light on, reply gives 18 to 28 °C.
3. Set `offline` on `sim/bedroom_ceiling_fan/fault` (T-007). `say "Turn on the bedroom fan"` -> not responding, `failed` "device offline" quickly (T15).
4. Kitchen light off. `say "Turn on the kitchen light and the bedroom fan"` -> light on, reply says the fan failed (T16).
5. UC-28-E2: `say "What's on?"` -> fan reported as not responding.
6. Turn the kitchen light off in HA first, then set `ignore_commands` on it, then `say "Turn on the kitchen light"` -> about 3 s, `timeout`, reply never says done.
7. E1: set both to `normal`, ask again -> works.
8. `cd backend && pytest`.
