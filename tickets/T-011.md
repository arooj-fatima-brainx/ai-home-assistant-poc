# T-011: Log in with rate limit
- Milestone: M1
- Depends on: T-010
- Use cases: UC-09
## Goal
`POST /api/auth/login` checks the password and sets the cookie; 5 failed tries per email and IP in 15 minutes block further tries with `429`.
## Definition of Done (copied from use cases)
- [ ] AC-09.1 Given the right email and password, when the user logs in, then the response is `200` with the user, and a `Set-Cookie` header with `HttpOnly`, `SameSite=Lax` and a 24-hour expiry.
- [ ] AC-09.2 Given the user logged in, when they call a protected route with the cookie (`GET /api/auth/me`), then it returns `200`.
- [ ] AC-09.3 Given the user logged in, when the response body is checked, then it does not contain the token (the browser only keeps it in the cookie).
- [ ] UC-09-E1: Given a wrong password, when logging in, then the response is `401` "Wrong email or password".
- [ ] UC-09-E2: Given an email that is not registered, when logging in, then the response is the same `401` "Wrong email or password" (no hint whether the email exists).
- [ ] UC-09-E3 (T22): Given 5 failed logins for one email from one IP within 15 minutes, when a 6th attempt is made (even with the right password), then the response is `429` "Too many login attempts. Try again later." until 15 minutes have passed.
- [ ] UC-09-E4: Given the cookie value is changed by hand, when a protected route is called, then the response is `401` "Not logged in".
- [ ] UC-09-E5: Given the token has expired, when a protected route is called, then the response is `401` "Not logged in".
- [ ] All tests pass. Reviewer approved. Verifier passed.
## Technical notes
- `backend/app/auth/router.py`: `POST /api/auth/login` -> `200` with `UserOut`; same cookie helper as sign-up. Same `401` "Wrong email or password" for wrong password and unknown email (verify against a dummy hash for unknown emails so timing is similar).
- `backend/app/auth/rate_limit.py`: in-memory counter keyed by `(email, ip)` with timestamps; 5 failures in 15 minutes -> `429` "Too many login attempts. Try again later." even with the right password. Success resets the counter. Make the clock injectable for tests.
- `current_user`: tampered or expired token -> `401` "Not logged in".
- Tests: `tests/test_auth_login.py` (cookie flags, no token in body, E1 to E5 with a fake clock and a short expiry).
## Manual test steps
1. ```bash
   curl -i -c a.txt -X POST $BASE/auth/login -H 'Content-Type: application/json' \
     -d '{"email":"ali@example.com","password":"secret123"}'
   ```
   Expect `200`, `Set-Cookie` with `HttpOnly`, `SameSite=Lax`, `Max-Age=86400`, and no token in the body.
2. `curl -i -b a.txt $BASE/auth/me`. Expect `200`.
3. E1, E2: log in with a wrong password, then with `nobody@example.com`. Both `401` "Wrong email or password".
4. E3: 5 wrong logins for `ali@example.com`, then the right one. Expect `429`. `docker compose restart backend` resets it.
5. E4: change one character of the token in `a.txt`; `/auth/me` gives `401` "Not logged in". Log in again.
6. E5: `JWT_EXPIRE_MINUTES=1` in `.env`, `docker compose up -d backend`, log in, wait 70 s, `/auth/me` gives `401`. Put the value back.
7. `cd backend && pytest`.
